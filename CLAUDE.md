# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A macOS SwiftUI app ("Performance App") that displays live CPU load (overall, per-core, and split by Performance/Efficiency core type) and static hardware/GPU specs. Built incrementally with Claude Code as a learning project (see README.md).

## Commands

The project is a plain Xcode project at `Performance App/Performance App.xcodeproj` (no workspace, no SPM dependencies). Scheme name: `Performance App`.

Build, run, and test normally via Xcode (⌘B / ⌘R / ⌘U) with the "My Mac" destination — this is a macOS app, not iOS, even though iOS/visionOS simulator destinations also appear in the destination list.

CLI equivalents:

```sh
# Build
xcodebuild -project "Performance App/Performance App.xcodeproj" -scheme "Performance App" -destination "platform=macOS" build

# Run all tests
xcodebuild -project "Performance App/Performance App.xcodeproj" -scheme "Performance App" -destination "platform=macOS" test

# Run a single test
xcodebuild -project "Performance App/Performance App.xcodeproj" -scheme "Performance App" -destination "platform=macOS" test \
  -only-testing:"Performance App Tests/SysctlTests/int32ReadsPhysicalCoreCount()"
```

Tests use the **Swift Testing** framework (`import Testing`, `@Test`, `#expect`) — not XCTest. The test target (`Performance App Tests`) is hosted inside the app target.

**Known issue:** running the test target can intermittently crash with `EXC_BREAKPOINT` inside `Runner._applyScopingTraits`, with a different subset of tests failing each run. This reproduces even on trivial tests with no logic connection to each other, and coincided with other environment instability (an Xcode crash, a run that hung on a "Replace" dialog). Treat it as environment/tooling flakiness, not a signal that the affected test's logic is wrong, unless a failure is consistent across repeated runs.

## Architecture

**Navigation shell:** `ContentView.swift` is a `NavigationSplitView` sidebar switching between four independent screens — `CPULoadView`, `MemoryView`, `ProcessesView` (all live-polling), and `HardwareInfoView` (static specs). Each screen owns its own state; there's no shared app-wide model.

**Shared code** lives in `Shared/` (`SystemSampling.swift`, `HistoryModels.swift`, `HistoryStore.swift`, `HistoryGapSegmentation.swift`, `HistoryCoding.swift`, `ProcessRanking.swift`, `ProcessHelperXPC.swift`, `Sysctl.swift`), compiled into both the "Performance App" and "Performance App Helper" targets so the app's live views and the helper's background recorder call the exact same sampling/ranking code instead of maintaining duplicate copies. **This is a plain Xcode group with explicit per-target Compile Sources membership, not a synchronized folder** — unlike `Performance App/` and `Performance App Helper/`, dropping a new file into `Shared/` on disk does *not* automatically add it to either target. Use "Add Files to…" and check both target boxes, or it'll silently compile into only one target (or neither) and produce a confusing "cannot find type" error in the other.

`SystemSampling.swift` holds every raw system-reading function, all `nonisolated` so they're callable from the app's `@MainActor`-isolated monitors, from the helper's background queue, and from synchronous test functions alike: `CPUSampling` (tick reads + delta aggregation + P/E layout), `MemorySampling` (`host_statistics64` snapshot), `ProcessSampling` (the `libproc` sweep, privilege-gated — see below), and `SystemClock.bootTime()` (`kern.boottime`, not privilege-gated, used to clamp history queries to "since boot").

**CPU monitoring pipeline** (`CPUMonitor.swift`): a `@MainActor @Observable` class that polls `CPUSampling.readTicks()`/`.aggregate(...)` once a second via an async loop (`start()`, driven by SwiftUI's `.task` lifecycle — no `Timer`, no Combine). Key points for anyone touching this file:
- The "Total"/"Performance"/"Efficiency" aggregate numbers are **sums** of their member cores' usage, not averages — matching Activity Monitor/`top` convention (e.g. a fully-busy 4-core group reads "400%"). This is intentional; don't "fix" it back to an average.
- `history` is now only the **local, in-session fallback** (rolling 60 minutes, lost on quit) used when the background helper (below) isn't reachable — the primary chart data comes from recorded history instead.

**Static hardware/GPU info** (`HardwareInfo.swift`, `GPUInfo.swift`): one-shot (not polled) facts gathered via `sysctlbyname` and Metal (`MTLCopyAllDevices`), rendered by `HardwareInfoView.swift` as grouped label/value lists (`HardwareInfoSection`/`HardwareInfoItem`, defined in `HardwareInfo.swift` and reused by `GPUInfo.swift` — don't duplicate these types). Every field is read defensively (`guard`/optional chaining) and simply omitted from the list if the current Mac doesn't report it (e.g. `hw.perflevel1.*` on Intel, or discrete-GPU-only `MTLDevice` properties on Apple Silicon) rather than showing a placeholder or guessing.

**Memory monitoring** (`MemoryMonitor.swift`, `MemoryView.swift`): same `@MainActor @Observable` + `.task`-driven polling pattern as `CPUMonitor`, reading `MemorySampling.readSnapshot()` once a second. "Used" is `active + inactive + wired + compressed`, deliberately *not* `total - free`: macOS's aggressive disk caching makes raw "free" memory tiny and misleading. The "Used" bar is a custom segmented view (`SegmentedUsageBar`) colored per kernel category, each with a `.help()` tooltip. `history` here is the same kind of local 60-minute fallback as `CPUMonitor.history`.

**Per-process CPU monitoring via a privileged helper daemon** (`ProcessHelperClient.swift`, `ProcessesView.swift`, plus `Shared/ProcessHelperXPC.swift` and `Shared/ProcessRanking.swift`): `ProcessSampling`'s `libproc` calls (`proc_listallpids`, `proc_pid_rusage`) return `EPERM` for the main app, which is an unprivileged, non-root caller — confirmed to fail identically in a snippet, an Xcode Preview, a Debug `⌘R` launch, and a Release Finder launch. There is no per-core/per-thread equivalent of this at all, for anyone or anything — not even Activity Monitor shows "which process is on which core"; Apple treats exact core placement as an internal scheduling detail with no public API.

The working architecture: `Performance App Helper` is a plain command-line-tool target, registered via `SMAppService.daemon(plistName:)` as a `LaunchDaemon` that runs as root, answering requests from the main app over XPC (`NSXPCConnection`, Mach service `com.performanceapp.helper`). This genuinely works with free, local signing — no paid Apple Developer Program membership required. Non-obvious things that cost real debugging time to find, in case this needs touching again:

- **The main app target must not have App Sandbox enabled.** `SMAppService` refuses to register a daemon with "target executable must be sandboxed because the app is sandboxed" if the calling app is sandboxed and the daemon isn't — and a root daemon fundamentally can't be sandboxed to match its caller. If App Sandbox capability is ever re-added (e.g. by Xcode's "Automatically manage signing" regenerating a default entitlements file), registration breaks with a generic "Operation not permitted" that says nothing about sandboxing — the real reason only appears in the system log (see below).
- **A real Team Identifier is required, but a free one is enough.** Pure ad-hoc signing ("Sign to Run Locally", `TeamIdentifier=not set`) fails registration outright with EPERM. Xcode's free "Personal Team" (any Apple ID, via "Setup Signing…" in Signing & Capabilities, no paid enrollment) is sufficient.
- **The two Copy Files build phases must be on the "Performance App" target** — not "Performance App Tests" or "Performance App Helper". Three similarly-named targets in the same dropdown makes this an easy mistake, and the failure mode ("Unable to read plist") doesn't point at the real cause. The phases: the helper executable into destination `Executables` (→ `Contents/MacOS`), and `com.performanceapp.helper.plist` into destination `Wrapper` with subpath `Contents/Library/LaunchDaemons`.
- **BackgroundTaskManagement pins the approved daemon binary by SHA256 checksum.** Rebuilding the helper after it's already registered makes the old approval stop matching the new binary; the daemon then fails to spawn with `last exit code = 78: EX_CONFIG` (visible via `sudo launchctl print system/com.performanceapp.helper`, not through the app itself). Every time the helper's code changes: click "Unregister Helper (dev)" in the Processes view, then fully quit and relaunch the main app to force a fresh `register()` against the current binary.
- **The free signing identity doesn't travel with `git`.** `DEVELOPMENT_TEAM` is a committed build setting, but the actual certificate lives in the local machine's keychain/Xcode account. A fresh clone (or new Apple ID/machine) needs "Setup Signing…" redone for both the "Performance App" and "Performance App Helper" targets before any of this works.
- **`/usr/bin/log show --last Nm --predicate 'eventMessage CONTAINS "performanceapp"'` is the real debugging tool here, not the error Swift sees.** `smd`/`backgroundtaskmanagementd` log the actual reason (sandbox mismatch, checksum mismatch, etc.); the `NSError` that bubbles up through `register()` is a generic, unhelpful "Operation not permitted" in every one of these distinct failure cases.
- Per-process usage follows the same **sum-not-average**, per-core-unit-of-100% convention as `CPUMonitor` — a process busy on 2 threads simultaneously reads "200%".
- **`rusage_info_v2.ri_user_time`/`ri_system_time` are raw Mach absolute-time ticks, not nanoseconds.** This was the real cause of an early, large (40-100x) discrepancy between the per-process sum and the Cores view's Total — initially misdiagnosed as sampling-interval dilution and as `kernel_task` being unattributed (both real but minor effects, not the dominant one). Confirmed empirically: a controlled 0.5-real-second busy loop reported a raw `ri_user_time` of ~20M, which is ~0.02s if treated as nanoseconds directly but lands in the right ballpark once converted through `mach_timebase_info` (numer=125, denom=3 on Apple Silicon — i.e. 1 tick ≈ 41.67 ns, explaining almost exactly a ~42x understatement). Fixed by converting both fields via `ProcessRanking.nanoseconds(fromMachTicks:timebase:)` before summing in `ProcessSampling.sampleProcessTimes()`. Don't assume any `libproc`/`rusage` time field is already in nanoseconds without checking — these structs aren't in Apple's indexed Swift/ObjC docs, and ticks-vs-nanoseconds is an easy, silent unit mismatch.
- **The remaining (much smaller) per-process-sum-vs-Total gap is expected, not a bug.** `host_processor_info`'s Total counts every tick on every core, including kernel/interrupt work that per-process `rusage` summation can't attribute to any enumerable process — `kernel_task`/PID 0 in particular does not appear via `proc_listallpids`/`proc_pid_rusage` the way user processes do.

**Persistent background history recording** (`HistoryRecorder.swift` in the Helper target; `HistoryStore.swift`, `HistoryModels.swift`, `HistoryGapSegmentation.swift`, `HistoryCoding.swift` in `Shared/`): the helper doesn't just answer on-demand XPC requests — once registered, it starts at boot (`RunAtLoad`/`KeepAlive` in `com.performanceapp.helper.plist`) and continuously records CPU, memory, and top-5-process samples once a second to a local SQLite database, independent of whether the main app is even running. Opening the app shows history since boot (or the latest 24h, whichever is shorter), not just whatever's accumulated since the window opened.

- **Database location:** `/Library/Application Support/com.performanceapp.helper/history.sqlite`, root-owned (the helper always runs as root). The app never opens this file directly — it only ever asks the helper for data over XPC (`fetchCPUHistory`/`fetchMemoryHistory`/`fetchProcessSummary`/`fetchPeaks`/`resetPeaks`, replies are binary-plist-encoded `Data` via `HistoryCoding`, same "`Data`/`[String: Any]` over custom `NSSecureCoding` types" reasoning as `fetchTopProcesses`). This sidesteps any root-owned-file-vs-unprivileged-reader permission question entirely, and keeps the helper as the single source of truth. To inspect it directly while debugging: `sudo sqlite3 "/Library/Application Support/com.performanceapp.helper/history.sqlite"`.
- **Raw per-second samples are always stored unaveraged.** Averaging only happens in `HistoryStore`'s `query...` methods, computed in SQL (`SUM`/`SUM of squares`/`MIN`/`MAX` per bucket, turned into mean/variance by `BucketStats`'s initializer) — so an arbitrarily long `HistoryRange` still returns a bounded ~720 points without ever discarding the underlying precision before query time.
- **`BucketStats` carries mean, standard deviation, min, and max per bucket, not just a mean.** A bare average would hide a brief spike once enough samples get bucketed together (a 1-second spike to 800% barely moves a 2-minute bucket's mean) — the charts draw a faint min-max envelope and a tighter ±1σ band (clamped to `[min, max]`) behind the mean line specifically so spikes stay visible at any zoom level. Population variance is computed from running sums (`E[x²] − E[x]²`) and clamped to ≥0 before the square root, since floating-point rounding can push a near-constant series' computed variance slightly negative.
- **`peaks` is a separate table that pruning never touches.** It tracks the all-time high for CPU total/performance/efficiency, memory used, and the single busiest process-sample ever seen, each with its timestamp, updated via an upsert (`ON CONFLICT ... WHERE excluded.value > peaks.value`) during the same transaction as the regular flush — so it costs no extra writes and survives both the 24h retention window and reboots. The Reset button in each view's peaks row clears it.
- **Retention is `max(now - 24h, bootTime)`, recomputed on every prune** (roughly once a minute, plus once at helper startup) — a reboot therefore discards the previous boot's samples immediately, not just whatever falls outside the 24h window.
- **The helper buffers 1Hz samples in memory and flushes to SQLite roughly every 10 seconds**, not on every sample — one transaction per second would be unnecessary I/O for a background daemon that's supposed to stay light. `fetchCPUHistory`/`fetchMemoryHistory`/`fetchProcessSummary` all flush the pending buffer first, so a query always reflects up to the most recent sample rather than whatever was last committed.
- **Only the top 5 ranked processes are recorded per second** (vs. 15 shown live in the Processes view) — this is the dominant contributor to database size (~20MB at the 24h retention cap); it's a single constant (`HistoryRecorder.recordedProcessCount`) if it needs tuning. `queryProcessSummary`'s ranking uses SQL window functions (`PARTITION BY`/`ROW_NUMBER()`), not a correlated subquery referencing an outer aggregate — the latter is ambiguous in SQLite and was caught and fixed during review, not by a production symptom.
- **Gap segmentation** (`HistoryGapSegmentation.segments(_:maxGap:)`) splits a time-ordered series wherever two consecutive samples are further apart than ~2.5 bucket-widths (sleep, helper downtime), and the charts draw each run as its own Swift Charts `series:` so a gap reads as a visible break instead of a straight line silently bridging time that was never sampled. This is applied to every line in the CPU chart and to the Memory chart's dashed peak-line, but **not** to the Memory chart's stacked area fill — that already uses `foregroundStyle(by:)` to group its four category layers, and layering a second per-segment `series` on the same marks would fight that grouping. A gap in the stacked fill (not the line or tooltip) is the one accepted visual gap in this feature.
- **Each of `CPULoadView`, `MemoryView`, and `ProcessesView` owns its own `ProcessHelperClient`** and independently calls `registerHelperIfNeeded()` in its own `.task` — consistent with "no shared app-wide model" above. This is safe because `NavigationSplitView`'s detail pane only ever instantiates the one currently-selected screen, so there's no real concurrent-registration race, and it means the helper gets registered regardless of which screen the user opens first (not just Processes).
- **Every history-driven view falls back to its own local, in-session `CPUMonitor.history`/`MemoryMonitor.history`** whenever the helper returns no recorded data (not registered, unreachable, or just hasn't flushed anything yet) — never a blank chart while the app itself is running and taking live readings.

**GPU load monitoring** (`Shared/PowerMetricsReader.swift`, wired into `HistoryRecorder` in the Helper target; GPU row/chart in `CPULoadView.swift`): system-wide GPU load has no public syscall equivalent to `host_processor_info`, but the helper already runs as root, and `/usr/bin/powermetrics` (an Apple-shipped, documented *tool*, even though its output schema isn't) requires exactly that — so the helper launches it as a long-running subprocess (`powermetrics -s gpu_power -i 5000 -f plist`) and parses its continuous, NUL-separated plist output stream. This is a genuinely different sampling shape from everything else in this app: a subprocess that streams on its own schedule, not a syscall polled on our own timer.

- **The real plist schema was confirmed by direct capture, not assumed from the man page.** `powermetrics -h` names a `gpu_power` *sampler*, which suggested a top-level `gpu_power` key — the actual output has no such key. The real data is a `gpu` dict containing `idle_ratio` (fraction of the sample the GPU was idle; `1 − idle_ratio` is the load fraction used directly, no conversion needed) and `gpu_energy` (an energy delta for the sample window, converted to milliwatts via `energy / (elapsed_ns / 1e9)`, treating the value as millijoules — the standard community convention for `powermetrics`'s `*_energy` fields, not an Apple-documented one). Don't assume a sampler's name on the command line matches its plist key; check a real capture.
- **Per-process GPU attribution was investigated and found genuinely unavailable, not just unreliable.** `powermetrics`'s `--show-process-gpu` flag is documented to add a `gputime_ms_per_s` field to each `tasks` entry. A real capture (`sudo powermetrics -n 1 -i 1000 -s gpu_power,tasks --show-process-gpu -f plist`) on this hardware/OS shows the field is absent from every single task — not present-but-zero, simply not emitted at all, for any process including the helper itself. This is the same category of wall as the per-core/per-thread CPU attribution limitation above: no public (or semi-public, reverse-engineered) mechanism exposes it here. If ever revisited, start by capturing real output again first — don't assume the man page's description of a flag reflects what the current OS version actually emits.
- **`powermetrics` must be launched as a persistent subprocess with incremental parsing, not invoked once per sample.** `PowerMetricsReader` owns a `Process`/`Pipe`, reads stdout via `readabilityHandler`, splits on the NUL byte separating consecutive plist documents, and restarts the subprocess if it ever exits unexpectedly — mirroring at the subprocess level the same `RunAtLoad`/`KeepAlive` resilience the daemon itself gets from `launchd`.
- **The parsing step is a pure function (`PowerMetricsReader.parseSample(from:)`) tested against a real captured fixture**, not synthetic guesses — the same "narrow testable seam" pattern used throughout this project, chosen here specifically because `powermetrics`'s output isn't a stable contract and a schema change should be caught by a test against real data, not discovered in production.
- **GPU samples arrive on their own ~5s cadence, independent of the recorder's 1 Hz tick**, and are folded into the same buffered-flush/prune/peaks pipeline as CPU/memory/process data (`gpu_samples` table, `.gpuLoad` peak metric) — no separate storage story was needed.
- This is Phase 1 of a larger planned "Power & Thermal" feature; Phase 2 (CPU/ANE power, thermal pressure, battery, `ProcessInfo.thermalState`) extends the same subprocess with more samplers rather than redesigning it.
